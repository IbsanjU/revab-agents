# Project Memory

In-repo Copilot memory — version-controlled, shared across machines and sessions.
Agents read this at session start and append learnings via the artifacts `knowledge_append` MCP tool (which writes to `knowledge/learnings.md`) or by directly editing this file.

## Framework facts

- **Architecture**: `revab-agents` is framework-only. It has no `tests/` and never runs Playwright/Cucumber/Allure against itself. Every test-authoring/execution/reporting operation targets a **project** declared in `projects/manifest.json` (index) + `projects/<name>/project.json` (per-project config; legacy single-file `projects.manifest.json` still supported as fallback), resolved via `utils/manifest.ts` (the trust boundary — never accept a raw `repoPath`/`repoUrl` from a payload/tool arg).
- **MCP servers** (local HTTP, stateless, `.vscode/mcp.json`):
  - `jira` :7311 — `jira_search`, `jira_get_issue`, `jira_get_epic_children`, `jira_add_comment`, `jira_create_issue` (dryRun default), `jira_bulk_create_issues` (dryRun default; per-row dedup search + partial-failure-tolerant batch create; each draft may carry a `transitionName` applied right after a successful, non-duplicate create), `jira_search_users` (resolve name/email -> accountId, optionally scoped to a project), `jira_assign_issue` (dryRun default; requires a resolved accountId, never a raw name), `jira_update_issue` (dryRun default), `jira_bulk_update_issues` (dryRun default; per-row `fields` update and/or `transitionName`, partial-failure tolerant — same transition-resolution as `jira_transition_issue`), `jira_transition_issue` (dryRun default), `jira_get_boards`/`jira_get_sprints`/`jira_get_backlog` (Agile REST reads), `jira_move_to_sprint` (dryRun default), `jira_get_sprint_report` (status/unassigned/missing-field counts for a sprint), `jira_save_issue` (asks for a project folder before saving locally) — `jira_delete_issue`'s implementation remains in source but its `registerTool` call is commented out (not registered), so the running server cannot delete issues; see `knowledge/conventions.md`. Transition lookup/apply logic is shared via `findTransition`/`applyTransition` helpers in `mcp-servers/jira/index.ts` (used by `jira_transition_issue`, `jira_bulk_create_issues`, and `jira_bulk_update_issues`).
  - `confluence` :7312 — `confluence_search`, `confluence_get_page` (format: text/html/structured — structured expands accordion/expand/tabs macros instead of flattening them), `confluence_get_children`, `confluence_get_attachments`, `confluence_download_attachment`, `confluence_get_comments`, `confluence_extract_links`, `confluence_create_page` (dryRun default), `confluence_update_page` (dryRun default), `confluence_add_comment` (dryRun default), `confluence_delete_page` (dryRun default), `confluence_save_page` (asks for a project folder before saving HTML+structured+metadata locally), `confluence_upload_attachment` (dryRun default — attach local images/diagrams to a page, returns an <ac:image> embed hint)

  - `artifacts` :7314 — `list_files`, `read_repo_file`, `knowledge_append`, `knowledge_search` (greps knowledge/** and projects/**/*.md for prior work) — scoped to this repo only
  - `media` :7319 — `get_file_metadata` (image/PDF/DOCX/generic metadata as JSON), `read_pdf_text`, `read_docx_text`, `read_excel_rows`/`read_csv_rows` (xlsx/xls/csv -> structured rows keyed by header row, for bulk ticket intake), `create_pdf`, `create_docx` (styled, accent-color support) — resolves paths against this repo by default or a manifest `project`'s repoPath if given; plus `ocr_image` (local tesseract.js OCR: text + blocks with bbox/confidence), `ocr_pdf` (page-by-page OCR of scanned PDFs via pdf-parse getScreenshot), `read_diagram` (draw.io XML / Mermaid / PlantUML -> { nodes, edges } graph via utils/diagramParse.ts; raster -> use ocr_image, best-effort), `create_diagram` (Mermaid -> SVG/PNG via npx @mermaid-js/mermaid-cli); uses `pdf-parse`, `mammoth`, `image-size`, `file-type`, `pdfkit`, `docx`, `tesseract.js`, `xlsx` (installed from SheetJS's own CDN tarball, not the npm registry — the npm-published `xlsx` build has unpatched prototype-pollution/ReDoS advisories; see `package.json`'s `xlsx` dependency)
  - `notify` :7321 — `notify_teams` (Adaptive Card to TEAMS_WEBHOOK_URL), `notify_email` (Outlook via Microsoft Graph GRAPH_* or smtp.office365.com SMTP_* fallback, nodemailer) — both dryRun default; worker sends automatic completion notices only for tasks that opt in via payload `notify` ("teams" or {channel:"email",to:[...]}, NOTIFY_EMAIL_TO fallback)
  - `git` :7322 — `git_log`, `git_branches`, `git_search` (mode:"messages" greps commit messages with `--all`; mode:"content" runs `git grep` at one ref), `git_diff`, `git_show` — all read-only, take an optional `project` (manifest-resolved repoPath; omit to use this repo itself), and shell out to the real `git` binary via `spawn(..., {shell:false})` (argv array, not a shell command line) so free-text queries/refs can't be interpreted as shell syntax.   - `playwright-runner` :7316 — `run_bdd`, `run_playwright`, `get_test_files` — all take `project`, execute in that project's resolved repoPath

  - `codegen` :7318 — `scaffold_feature` (requires `source` citation), `scaffold_step`, `scaffold_page`, `detect_conventions` — writes into the target project's `testPaths`
  - `playwright` :7315 — official `@playwright/mcp` via `npm run serve:playwright` (npx, local — target-agnostic interactive browser automation)
  - Shared infra: `mcp-servers/shared/server.ts` (`startMcpHttpServer`, `textResult`, `errorResult`), `mcp-servers/shared/http.ts` (`apiGet`, `apiPost`, `apiPut`, `apiDelete`, `apiGetBinary`, `authHeaders`, plus exported `buildUrl`/`handleJson` reused by other HTTP-backed servers — auth is per-service via `setAuthService("jira"|"confluence"|"jtmf")`, called once at each server's startup; `authHeaders()`/`apiGet`/etc. take no service argument, they read whichever service that process declared, preferring `<SERVICE>_EMAIL`/`<SERVICE>_API_TOKEN`/`<SERVICE>_AUTH_MODE` and falling back to the shared `ATLASSIAN_*` vars), `mcp-servers/shared/githubHttp.ts` (`githubGet` — `GITHUB_TOKEN`-based auth, falling back to the `gh` CLI's own authenticated session via `ghApiFallback` when `GITHUB_TOKEN` is unset (github.com only, not GHES); `defaultGithubOrg`), `utils/fsSafety.ts` (`resolveWithinRoot`, the reusable path-containment check), `utils/saveSuggestion.ts` (`suggestProjectFolder`/`buildSaveConfirmationPrompt` for the ask-before-save pattern), `utils/confluenceMacros.ts` (`expandConfluenceMacros`), `utils/jiraLinks.ts` (`buildJiraIssueUrl`, shared by jira/jtmf servers), `utils/notify.ts` (sendTeams/sendEmail/buildTeamsPayload, shared by notify server + worker), `utils/diagramParse.ts` (parseDiagram/parseDrawio/parseMermaid/parsePlantuml). All MCP servers bind to 127.0.0.1; optional MCP_SHARED_SECRET enforces an x-mcp-secret header
- **Gateway (how the tools are actually served)**: `npx revab start` (or `npm run serve:gateway`) hosts **every** tool from all 11 servers in ONE process on :7300 — MCP at `POST /mcp`, plus a REST fallback at `POST /api/<server>/<tool>` for when MCP isn't available (CI, curl, non-MCP editors); `GET /api/tools` lists everything with schemas and a `risk` (read/write) flag, `GET /health` reports liveness + tool count. Both surfaces call the same handlers, so the manifest trust boundary and dryRun-first defaults apply identically. `.vscode/mcp.json` therefore has just TWO entries: `gateway` and `playwright` (the official `@playwright/mcp` browser server, which the gateway does not host) — never register the individual servers as well, that duplicates every tool. The per-server `npm run serve:<name>` scripts still work for debugging one server (`npm run serve:mcp:individual` runs the old 11-port fan-out).
- **CLI**: `npx revab init` (scaffold `.env` + `.vscode/mcp.json` + manifest index), `npx revab doctor` (diagnose env/auth/base URLs/projects/gateway — run this FIRST when anything misbehaves; it names the variable and the fix), `npx revab start`. Built to `dist/` via `npm run build`.
- **Manifest**: `projects/` dir (zod-validated by `utils/manifest.ts`): `projects/manifest.json` index + `projects/<name>/project.json` per project, with per-project artifacts co-located (`app-model.md`, `downloads/`, `reports/`, `test-plans/`; `resolveProjectArtifactsDir()`); legacy root `projects.manifest.json` still works as fallback. Each project.json: `name`, `repoPath`/`repoUrl`+`branch`, `testPaths`, `jira`/`confluence`/`jtmf` ids, `execution.mode` (`local`|`browserstack`|`custom`, defaults `local` — BrowserStack only if detected in the target repo, never assumed).
- **Orchestrator**: file queue `.queue/pending|running|done|failed`; handlers in `agents/registry.ts` — `run-bdd`/`generate-report` require `payload.project`; `typecheck` stays scoped to this framework repo; CLI `npm run task -- enqueue|status|types|reclaim`; worker `npm run worker` — per-task timeout (WORKER_TASK_TIMEOUT_MS, default 30min), one opt-in retry (`payload.retryOnFailure: true`), opt-in completion notifications (`payload.notify`), and plan traceability (`payload.plan` = knowledge/plans path). Worker auto-sweeps stale `running` tasks (crash recovery) via `reclaimStale()`; queue root and manifest path are env-overridable (`QUEUE_ROOT_DIR`, `MANIFEST_PATH_OVERRIDE`) for tests.
- **Agents (GENERATED — never hand-edit)**: authored as typed specs in `prompts/agents/*.ts`; `npm run build:prompts` renders them into `.github/agents/*.agent.md` (Copilot), `.claude/agents/*.md` (native Claude Code subagent, one per persona incl. orchestrator), `AGENTS.md`, and `.github/copilot-instructions.md`, inlining the hard rules into every persona so they load on ANY model. On Claude Code, run `claude --agent orchestrator` to make the root session the orchestrator; it dispatches a specialist directly via `subagent_type: "<name>"` against `.claude/agents/<name>.md`. Without a Task-style subagent tool it falls back to the async queue; with neither, it must stop and name the specialist rather than do that specialist's job inline (the failure this convention closes — verified by actually running `claude --agent orchestrator` from this repo and confirming the Agent tool lists exactly the 9 specialist subagent_types, plus by asking a plain `claude -p` session in this repo which subagent_types its Agent tool sees). `npm run build:prompts -- --check` fails CI on drift. Editing a generated file is always wrong — edit the spec and rebuild. 10 personas (planner, orchestrator, researcher, test-planner, automation, reporter, documenter, importer, self-improve, bsa) — all operate on a manifest-resolved `project`. Planner-first is hard rule 13: non-trivial work needs a finalized, user-approved plan before execution, saved under `projects/<project>/plans/` for project-specific work or `knowledge/plans/framework/` for framework-only work; researcher is strictly read-only (suggest-then-pull via ask-before-save tools incl. `github_save_file`) and now also searches local git history/branches (`git/*`) across every branch, not just the current one. `bsa` is the entry point for requirements arriving as chat/Excel/CSV/docs rather than existing Jira tickets — parses input, drafts tickets to a required-fields template, routes assignees via `projects/<project>/team-roster.json`, bulk-creates (dryRun-first), and reports sprint/backlog health; never deletes (see jira_delete_issue note above).
- **Skills**: `skills/*/SKILL.md` — `analyze-test-failures`, `detect-execution-convention`, `upload-to-jtmf`, `update-jira-epic`, `extract-requirements-from-image`, `extract-requirements-from-video`, - **Knowledge**: `knowledge/learnings.md` (dated session entries) + `knowledge/conventions.md` (team rules) + `knowledge/app-model/<project>.md` (living app maps) + `knowledge/reports/<project>/<date>.md` (consolidated project reports) + `knowledge/plans/<project>/<date>-<slug>.md` (planner-approved plans). New per-project artifacts should prefer `projects/<name>/` (app-model.md, downloads/, reports/, test-plans/).
- **Tool vocabulary**: specs use portable names (`Read`, `Grep`, `Glob`, `Edit`, `Write`, `Bash`, `Task`, `WebFetch`) plus `mcp__<server>__<tool>`; the portable→VS Code mapping (`read/readFile`, `search/textSearch`, `edit/editFiles`, `execute/runInTerminal`, `Task`→`agent`, …) lives once in `prompts/shared/skeleton.ts`, verified against VS Code's own tool reference (code.visualstudio.com/docs/agents/reference/ai-features-cheat-sheet) — `execute/runTask`/`read/getTaskOutput` do NOT exist there, only `execute/createAndRunTask`. Per-agent tool lists are minimal and wildcard-free; `npm run eval` fails if an agent loses a tool its own flow requires.
- **VS Code real subagent dispatch (v1.106+ custom-agents system)**: `.github/agents/orchestrator.agent.md`'s frontmatter carries a real `agents: ['planner', 'researcher', ...]` field (every other persona's name) plus `'agent'` in its `tools:` list — VS Code's own required pairing for a parent agent to dispatch named subagents as an actual tool call, not just prose. Every other persona's `.agent.md` omits `agents:` and has no `'agent'` tool, so it cannot itself dispatch further. This mirrors `.claude/agents/*.md`'s Task-tool dispatch on Claude Code — both hosts now have a *real* delegation mechanism, generated from the same `prompts/agents/*.ts` specs (`renderAgentMarkdown`'s `siblingNames` param populates VS Code's `agents:`; `renderClaudeSubagentMarkdown` handles Claude Code).
- **Multi-agent execution modes — see `docs/multi-agent-architecture.md` for the full cited reference.** Parallel dispatch works and is verified in this repo: `claude --agent orchestrator` dispatching two independent specialists (e.g. `researcher` + `planner`) in one turn genuinely ran them in parallel (confirmed via transcript, 2026-07-30) — the orchestrator spec's `always` list now explicitly instructs parallel dispatch for independent steps. Claude Code numeric limits: concurrent-subagent cap 20/session (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), total-spawn cap 200/session (`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`), nesting depth 3 by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`) — none of our specialist specs hold `Task`, so none can nest regardless. Background subagents run by default on Claude Code (v2.1.198+) with a reduced fixed tool set; this is unrelated to `orchestrator/queue.ts`'s own file-based async queue (deterministic npm-script task types only: `run-bdd`/`generate-report`/`typecheck`/`import-agents` — it cannot run an LLM persona) and unrelated to GitHub's cloud Copilot coding agent (a different product, not wired into this repo).
- **Only `orchestrator` is user-selectable, across EVERY GitHub Copilot custom-agents surface (2026-08-05, corrected same day).** `.github/agents/*.agent.md` is read by VS Code, Visual Studio, GitHub Copilot CLI, and Copilot's cloud coding agent — not just VS Code — and two different documented schemas apply: VS Code's own docs describe an `agents: [...]` allow-list plus an override rule for `disable-model-invocation: true`; GitHub's canonical cross-surface reference (`docs.github.com/en/copilot/reference/custom-agents-configuration` — what Copilot CLI/Visual Studio/the cloud agent actually implement) has NO `agents:` field and NO override for `disable-model-invocation`, where it simply means "must be manually selected," full stop. The first pass set `disable-model-invocation: true` on every specialist reasoning only from VS Code's docs — a real bug on any canonical-schema-only surface, since it would make every specialist unreachable by orchestrator there too. **Fixed same day**: specialists now set ONLY `user-invocable: false`, whose canonical wording ("cannot be manually selected, can only be accessed programmatically") already achieves the goal on every surface, VS Code included; `orchestrator.agent.md` keeps its VS-Code-only `agents: [...]` allow-list too (additive, harmless where unrecognized). **Claude Code has no equivalent field at all, confirmed by reading its complete "Supported frontmatter fields" table** (`.claude/agents/*.md`, no code change made there) — every subagent, built-in or custom, is always visible in the `@`-mention typeahead; the only enforcement available (`permissions.deny: ["Agent(<name>)"]`) blocks a subagent from being used by anyone including orchestrator, not a "hide from user only" switch. Don't invent one — see `docs/multi-agent-architecture.md` §8.
- **Orchestrator is a manager, not a worker (2026-08-05).** `skills/route-to-specialist/SKILL.md` (verb/object decision table + tie-breaks, replaces guessing which specialist owns a step) and `skills/review-delegated-work/SKILL.md` (the manager's independent check — scope/citations/dry-run/faithful-reporting — on what a specialist returns, before it's aggregated; a failed check goes back to the SAME specialist with the gap named, orchestrator never fixes it itself) are wired into `prompts/agents/orchestrator.ts`'s flow between dispatch and aggregate. Delegation-prompt structure (objective/output-format/tool-guidance/task-boundaries) and avoiding the "telephone game" between chained specialists follow Anthropic's own multi-agent research system writeup (anthropic.com/engineering/multi-agent-research-system) — see `docs/multi-agent-architecture.md` §10. Verified live with two real `claude --agent orchestrator` runs (routing decision stated with reasoning before dispatch; full review checklist run against a real specialist's actual citations before the final summary).
- **Repeated-correction-pattern detection (2026-08-05).** `npm run correction -- log` now prints a `⚠ REPEATED PATTERN` notice at log time (not just discoverable later via `list`) when the just-logged agent already has 2+ open corrections, naming the prior rule(s) — verified with two real CLI invocations. `skills/capture-correction/SKILL.md`'s new Phase 3.5 requires acting on it in the same turn: single-agent repeat → fold into that agent's `prompts/agents/<name>.ts` now; the same theme repeating across *different* agents → fold into `prompts/shared/conduct.ts` once, generic (a short topic hint is fine as an example, the rule itself must read as generic), not copy-pasted per agent. `self-improve`'s spec now explicitly owns editing the shared-conduct layer for cross-agent patterns and is framed as "the framework's teacher" in its description.
- **Quality gates**: `npm run typecheck`, `npm test`, `npm run check:conventions` (skill frontmatter, registry project guards, docs drift, and input coercion — every MCP boolean/number must be wrapped with `semanticBoolean`/`semanticNumber`), `npm run build:prompts -- --check` (prompt drift), `npm run eval` (per-agent capability + framework invariants). All run in CI.
- **Citations are validated**: `utils/citation.ts` rejects placeholders like `TBD` — a source must be a Jira key, `confluence:<id>`, `jtmf:<KEY>`, `app-model:<project>#<section>`, `transcript:<id>@00:12:34`, a repo path, or an https:// URL.
- **Anti-hallucination rule**: every generated test case/script/Jira/JTMF write must carry a source citation (Jira key, Confluence page id, transcript timestamp, or app-model reference). Missing citation blocks generation — ask, don't invent.
- **Verified data & freshness (hard rules 14-15)**: every line of a generated document must trace to an actually-fetched source (not just one citation per artifact); when sources disagree, the most recently updated one wins and the superseded one is named with its date, never silently dropped or blended. The `structure-project-data` skill is the generic playbook for reconciling scattered/conflicting Jira/Confluence/JTMF/GitHub/git data into one clean, dated project structure.
- **Media limits**: OCR and diagram reading are covered (`ocr_image`, `ocr_pdf`, `read_diagram`); speech-to-text is deliberately out of scope — `extract-requirements-from-video` still relies on manually supplied transcripts. Confluence viewer analytics needs Cloud Premium.
- **Ask before saving locally**: `confluence_save_page`/`jira_save_issue` (and `confluence_download_attachment`'s optional `project`) never write to disk until a `project` folder is confirmed — if omitted they return a suggested default (`<KEY>-XXX`) and a prompt to ask the user first.
- **Windows PATH fix** per terminal session: `$env:Path = "C:\Program Files\nodejs;$env:Path"; Set-ExecutionPolicy -Scope Process Bypass -Force`.
- **Testing/tooling**: `npm test` (Node built-in test runner via `tsx`, covers `utils/manifest.ts`, `utils/diagramParse.ts`, `orchestrator/queue.ts`, `scripts/check-conventions.ts`), `npm run check:conventions` (skill frontmatter + registry `payload.project` guard + docs-drift lint: every registerTool name must appear in README.md and knowledge/memory.md, every server in .vscode/mcp.json), CI at `.github/workflows/ci.yml` (typecheck+test+conventions on push/PR), `npm run knowledge:rotate` (archives old `knowledge/learnings.md` entries into `knowledge/learnings/<YYYY-MM>.md` past ~8KB).
